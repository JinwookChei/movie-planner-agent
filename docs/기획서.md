## 1. 도메인 확정 (명세 2.1)

### 1.1 외부 API 3종

| # | API | 주는 정보 | 쓰는 엔드포인트 | 인증 |
|---|---|---|---|---|
| 1 | **KOBIS 오픈 API** (영화진흥위원회) | 후보 영화(일별 박스오피스), 러닝타임, 관람등급, 장르 | `boxoffice/searchDailyBoxOfficeList.json`, `movie/searchMovieInfo.json` | 쿼리 `key` |
| 2 | **TMDB API** | 박스오피스 집계에 아직 없는 **신작 개봉 예정작**과 그 러닝타임 | `GET /3/discover/movie` (region=KR, release_date 범위), `GET /3/movie/{id}` | 쿼리 `api_key` |
| 3 | **카카오 로컬 API** | 지역 영화관의 이름, 주소, 링크 | `GET /v2/local/search/keyword.json` (category_group_code=CT1) | 헤더 `Authorization: KakaoAK {key}` |

**TMDB를 추가한 이유**: KOBIS 박스오피스는 지난 날짜의 집계만 준다(기준일 = min(목표일, 어제)). 그래서 오늘 이후 목표일 사이에 개봉하는 영화는 KOBIS 후보에 나오지 않는다. TMDB가 이 빈틈을 채운다 (F3002 "다른 API로 보충").

**같은 영화를 하나로 합치는 방법**: KOBIS와 TMDB는 서로 다른 ID를 쓴다. 그래서 공백을 지운 영화 제목이 같으면 같은 영화로 보고, 겹치면 KOBIS 쪽 정보를 쓴다.

### 1.2 출처와 이용 조건 (NF3007)

2026-11-20 웹 검색으로 확인한 내용이다. **공식 문서에서 수치를 확정하지 못한 칸은 "미확정"으로 남겼다.** 제출 전에 표의 확인처에서 직접 보고 채운다.

| API | 출처 | 호출 한도 | 약관 · 출처 표기 | 이 서비스의 사용량 |
|---|---|---|---|---|
| KOBIS 오픈API | 영화진흥위원회 영화관입장권 통합전산망 (kobis.or.kr/kobisopenapi) | **미확정.** 회원가입 후 키를 바로 발급(심사 없음). 일별 박스오피스는 한 번에 최대 10건 | 출처(영화진흥위원회 KOBIS)를 표기한다. 전일 집계는 다음 날 오전까지 보정될 수 있다 | 요청 1건에 박스오피스 1회 + 상세 최대 10회. 같은 세션은 cache로 재호출하지 않는다 |
| TMDB API | The Movie Database (developer.themoviedb.org) | **미확정.** 예전 제한(10초당 40건)은 2019-12-16에 해제됐다는 안내가 있으나 공식 페이지로 확인하지 못함. 초과 시 429 | 비상업적 사용은 무료. 출처 표기 필수: "This product uses the TMDB API but is not endorsed or certified by TMDB." 문구와 TMDB 로고를 화면의 '정보/크레딧' 영역에 둔다. 상업적 사용은 별도 계약 | 재계획 2단계에서만 discover 1회 + 상세 최대 3회 |
| 카카오 로컬 (키워드로 장소 검색) | Kakao Developers (developers.kakao.com/docs/latest/ko/local) | **미확정.** 앱 단위 일간·월간 쿼터가 있고 [내 애플리케이션 > 통계 > 쿼터]에서 확인한다. 초과 시 429 | 카카오 개발자 운영정책을 따른다. 검색 결과를 서버에 영구 저장하는 것은 제한된다는 데브톡 안내가 있다 | 지역을 말한 요청 1건에 1회. 결과는 세션 메모리 cache에만 두고 DB에 저장하지 않는다(로그에는 호출 인자와 성공 여부만 남는다) |
| SSAFY GMS | SSAFY 제공 OpenAI 호환 게이트웨이 | 교육 과정 정책을 따른다 | 교육 목적 | 요청 1건에 analyze 1회 + respond 1회(되묻기는 analyze 1회) |

- 화면 표기: 세 화면 아래에 출처 줄과 TMDB 문구를 넣었다(`frontend/app.js` renderTop). TMDB 로고 이미지는 넣지 않았다 → 남은 일.

### 1.3 Tool 결과와 비교해야만 답할 수 있는 요청

| 요청 | Tool 없이 LLM만 쓰면 틀리는 점 |
|---|---|
| "내일 강남에서 2시 이후에 보고 7시 전에 끝내고 싶어" | 지금 상영작과 러닝타임을 모른다. 이미 내려간 영화를 추천하거나 러닝타임을 지어내 7시를 넘긴다. |
| "이번 주 토요일 3시 이후, 6시 전에 끝나는 영화" | 학습 시점 이후에 개봉한 신작을 모르고, 시간 계산도 근거 없이 한다. |
| "오늘 4시에 보고 5시 전에 끝나는 영화" | 조건에 맞는 영화가 없는데도 있다고 지어낸다. 맞는 영화가 없다는 근거(가장 짧은 러닝타임)를 대지 못한다. |

### 1.4 저장할 결과물
**관람 계획**: 영화명, 관람 날짜, 시작 시각, 종료 시각, 영화관(선택), 메모(선택), 생성 일시, 수정 일시.

### 1.5 위험 도메인 여부
해당하지 않는다. 면책 문구는 두지 않는다.

## 2. 서비스 시나리오 (명세 2.2)

### 2.1 추출할 조건

| 구분 | 필드 | 형식 | 예 | 비어 있을 때 |
|---|---|---|---|---|
| 기준 | `watch_date` | YYYY-MM-DD | 내일 → 2026-11-20 | **오늘**로 처리하고 답변에 "날짜를 말씀하지 않아 오늘 기준"이라고 밝힌다 |
| 기준 | `start_after` | HH:MM | 2시 이후 → 14:00 | `end_before`가 있으면 **되묻는다**. 둘 다 없으면 시간 판단 없이 후보와 러닝타임만 보여 준다 |
| 선호 | `region` | 문자열 | 강남 | 영화관 검색을 생략한다 |
| 선호 | `genre` | 문자열 | 액션 | 장르로 거르지 않는다 |
| 제약 | `end_before` | HH:MM | 7시 전 → 19:00 | 시간 제약이 없다. 예상 종료 시각만 보여 준다 |

- LLM은 **현재 메시지에서 나온 값만** 채운다. 나오지 않은 값은 `null`로 둔다 (F3005).
- 오후·오전이 불분명한 "3시"는 영화 관람 맥락을 고려해 **10시 미만이면 오후**로 해석한다. 해석한 내용은 답변에 밝힌다.

### 2.2 의도 분류 (3종)

| 의도 | 설명 | 흐름 |
|---|---|---|
| `plan` | 관람 계획 수립 | 계획 → 실행 → 판단 → (재계획) → 응답 |
| `fact` | 사실 조회 ("위키드 러닝타임 몇 분?") | 후보 조회와 상세 조회 후 제목으로 찾아 응답. 제약 판단은 하지 않는다 |
| `chat` | 인사, 사용법, 그 밖의 대화 | Tool 없이 바로 응답 |

- 계획 **저장**은 의도로 처리하지 않는다. 화면의 [저장] 버튼 → `POST /api/plans`로 처리한다. 사용자가 이미 고른 값을 저장하는 일이라 LLM이 판단할 필요가 없기 때문이다 (명세 2.3).
- 캘린더 등록은 심화 과제라 범위에서 제외한다.

### 2.3 되묻기 규칙 (Tool을 호출하기 전에 코드가 판정)
- `end_before`는 있는데 `start_after`가 없을 때 → "몇 시 이후에 보실 수 있나요?"
- `start_after`가 `end_before`와 같거나 더 늦을 때 → "시작 시각이 끝 시각보다 늦어요. 다시 알려 주세요."

### 2.4 시간이 겹치는 계획 (F3015)
같은 `watch_date`에서 `[start, end)` 구간이 겹치는 계획이 있어도 **저장은 한다**. 응답의 `overlaps`에 겹치는 계획 목록을 담아 보내고, 화면에서 경고로 보여 준다.

### 2.5 대표 요청 (검증 4.7용, 실제 데이터에 맞게 시각은 조정)

| # | 유형 | 요청 | 기대 동작 |
|---|---|---|---|
| R1 | 한 번에 충족 | "내일 강남에서 2시 이후에 영화 보고 7시 전에 끝내고 싶어" | 박스오피스 → 상세 → 영화관 검색. 맞는 영화와 "늦어도 시작해야 하는 시각"을 제시한다 |
| R2 | 재계획 | "내일 3시 이후에 보고 4시 45분 전에 끝나야 해" (11/20 데이터 기준으로 조정) | 상위 5편 중 맞는 영화가 0편 → 재계획 1(상위 10편으로 확장, 이미 조회한 상세는 재사용) → 맞는 영화를 찾는다 |
| R3 | 상한 도달 | "오늘 3시 이후에 보고 4시 전에 끝나야 해" | 재계획 3회 후 멈춘다. "가장 짧은 영화가 N분이라 X분 범위에는 맞는 영화가 없다"며 조건 조정을 되묻는다 |
| R4 | Tool 하나 실패 | R1과 같은 요청을 카카오 키를 비우고 실행 | 영화관 검색만 INVALID_KEY로 실패한다. 영화 추천은 정상으로 하고, 영화관 정보를 가져오지 못했다고 안내한다 |
| R5 | Tool 불필요 | "안녕! 뭘 할 수 있어?" | `chat` 의도로 분류되고 Tool 호출 없이 응답한다 |
| R6 | 되묻기 | "7시 전에 끝나는 영화 알려줘" | Tool 호출 없이 시작 가능 시각을 되묻는다 |
| R7 | 대화 맥락 | R1 다음에 "같은 조건으로 홍대에서" | `region`만 바뀌고 날짜와 시각은 유지된다. 영화관 검색만 다시 한다 |
| R8 | 미래 날짜 + 신작 | "이번 주 토요일 2시 이후, 7시 전" | 박스오피스는 어제 기준이라 추정이라고 밝힌다. 금요일 개봉작은 TMDB로 보충한다 |

## 3. Tool 설계 (명세 2.3) — Tool 정의서 초안

### 3.1 공통 규칙
- 응답 형식: `{"ok": true, "data": {...}}` 또는 `{"ok": false, "error": {"code": "...", "message": "..."}}`
- Tool은 예외를 밖으로 던지지 않는다. `Tool.run()`이 예외를 잡아 실패 코드로 바꾼다.
- 외부 API 호출에는 `timeout=10`을 둔다.
- 오류 메시지에는 키를 넣지 않는다. `scrub()`은 KOBIS, TMDB, 카카오 키 값을 모두 가린다.
  - 주의: `api_key=` 형태는 샘플 정규식에 걸리지 않는다. 그래서 키 값 자체로 한 번 더 가린다.
- 레지스트리의 각 Tool에는 `kind: "external" | "local"`을 둔다. 필수 Tool은 모두 `external`이다 (F3001).
- Agent에게는 `catalog()`로 이름, 설명, 입력 스키마만 넘긴다.

### 3.2 실패 코드

| 코드 | 뜻 | 재계획 대상 |
|---|---|---|
| `BAD_ARGUMENT` | 입력이 규격과 다르다 (빈 값, 날짜 형식 오류, 모르는 인자) | X |
| `INVALID_KEY` | 키가 없거나 틀렸다 | X (다시 해도 결과가 같다) |
| `UPSTREAM_ERROR` | 시간 초과, 서버 오류 | X |
| `NOT_FOUND` | 없는 식별자 | X (해당 항목만 제외) |
| `NO_DATA` | 조회는 됐지만 결과가 비었다 | 상황에 따라 |
| `NO_RUNTIME` | 러닝타임이 비어 있다 (도메인 전용) | X (해당 영화만 판단하지 않고 제외) |

### 3.3 Tool 목록

#### ① `get_box_office` — 외부 (KOBIS) · F3002
- **설명(LLM이 읽음)**: "볼 영화를 아직 정하지 않았을 때, 관람 후보 영화 목록을 얻으려고 가장 먼저 부른다."
- **입력**: `target_date?: str(YYYY-MM-DD)`, `top_n?: int = 5` (1~10)
- **기본값**: `target_date`가 없으면 오늘. 실제 조회 기준일은 `min(target_date, 어제)`.
- **출력**: `{basis_date, is_estimated, movies: [{movie_cd, movie_nm, rank, open_dt}]}`
  - `is_estimated`가 true면 요청한 날짜와 실제 조회한 날짜가 다르다는 뜻이다. 답변에서 밝힌다.
- **실패**: BAD_ARGUMENT(날짜 형식), INVALID_KEY(`faultInfo` 응답), NO_DATA, UPSTREAM_ERROR

#### ② `get_movie_detail` — 외부 (KOBIS) · F3003
- **설명**: "영화코드(movie_cd)로 러닝타임과 관람등급을 확인할 때 부른다. 시간 안에 볼 수 있는지 판단하기 전에 필요하다."
- **입력**: `movie_cd: str` (필수, ①의 출력에서 받는다)
- **출력**: `{movie_cd, movie_nm, show_tm: int, watch_grade: str|null, genres: [str]}`
- **실패**: BAD_ARGUMENT, NOT_FOUND, NO_RUNTIME, INVALID_KEY, UPSTREAM_ERROR

#### ③ `search_new_releases` — 외부 (TMDB) · F3002 보충
- **설명**: "관람 날짜가 오늘 이후일 때, 박스오피스 집계에 아직 없는 그 사이 개봉작을 보충하려고 부른다."
- **입력**: `from_date: str`, `to_date: str` (①의 `basis_date` 다음 날부터 `target_date`까지)
- **내부 동작**: discover에서 `region=KR`, `release_date.gte/lte`, `with_release_type=2|3`, `language=ko-KR`로 최대 3편을 고른 뒤, 각 영화를 `/movie/{id}`로 조회해 runtime을 얻는다.
- **출력**: `{movies: [{tmdb_id, movie_nm, release_date, show_tm: int|null}]}`
  - runtime이 0이거나 비어 있으면 `show_tm: null`로 두고, 판단 단계에서 NO_RUNTIME으로 제외한다.
- **실패**: BAD_ARGUMENT, INVALID_KEY(401), NO_DATA, UPSTREAM_ERROR

#### ④ `search_theaters` — 외부 (카카오 로컬) · F3004
- **설명**: "사용자가 지역을 말했을 때, 그 지역의 영화관 위치를 함께 안내하려고 부른다. 상영 영화는 알 수 없다."
- **입력**: `region: str` (필수), `size?: int = 5`
- **내부 동작**: `query="{region} 영화관"`, `category_group_code=CT1`
- **출력**: `{theaters: [{name, address, url, phone}]}`
- **실패**: BAD_ARGUMENT, INVALID_KEY(401), NO_DATA(결과 0건), UPSTREAM_ERROR
- **주의**: 영화와 영화관을 임의로 묶지 않는다. "○○ 상영관에서 △△ 상영"처럼 말하지 않는다.

### 3.4 Tool 사이의 데이터 연결
```
요청.watch_date ─┬─▶ ① get_box_office ──movie_cd[]──▶ ② get_movie_detail (영화마다 반복)
                 └─▶ (미래 날짜면) ①.basis_date+1 ~ watch_date ─▶ ③ search_new_releases
요청.region ──────▶ ④ search_theaters
```

### 3.5 Tool로 만들지 않는 것
- 시간 계산과 제약 판단 → `judge` 노드의 코드가 한다
- 계획 저장과 겹침 검사 → 계획 API와 저장소가 한다
- 같은 영화 합치기 → `execute` 노드의 코드가 한다

## 4. Agent 실행 흐름 (명세 2.4) — Agent 설계 문서 초안

### 4.1 그래프 (LangGraph)
```
START → analyze ─┬─(chat / 되묻기)──────────────────────▶ respond → END
                 └─(plan / fact)→ plan → execute → judge ─┬─(맞는 후보 있음 / 상한 도달 / 재계획 불가)─▶ respond
                                    ▲                     │
                                    └────(재계획)──────────┘
```

| 노드 | 수행자 | 하는 일 |
|---|---|---|
| `analyze` | **LLM** (구조화 출력) | 의도, 의도 판단 이유, 조건 추출, 쓸 Tool 후보를 고른다. 그 뒤 코드가 이전 조건과 합치고 되묻기 규칙을 판정한다 |
| `plan` | 코드 | LLM이 고른 Tool을 의존 순서로 정렬하고 인자를 채운다. 재계획일 때는 다음 전략을 적용한다 |
| `execute` | 코드 | 계획대로 Tool을 호출한다. 같은 Tool과 같은 인자의 결과는 **cache**에서 재사용한다. 실패하면 사유를 남기고 계속 진행한다 |
| `judge` | 코드 | 필요 시간을 계산하고, 맞는 영화 / 맞지 않는 영화 / 판단하지 않고 제외한 영화로 나눈다 |
| `respond` | **LLM** | `judge`의 결과만 근거로 답변 문장을 만든다. 숫자와 시각은 judge가 계산한 값을 그대로 쓴다 |

LLM이 할 일과 코드가 할 일을 나눈 이유: 의도 파악과 문장 만들기는 LLM이 잘한다. 시간 계산, 재계획 판단, Tool 순서는 규칙으로 정할 수 있어서 코드가 더 정확하고 테스트하기도 쉽다.

### 4.2 State
```python
class State(TypedDict, total=False):
    session_id: str
    run_id: str                 # 요청 1건마다 새로 발급
    user: str                   # 현재 메시지
    memory: dict                # 이전 조건, 이전 추천 요약, 최근 대화 (4.5)
    intent: str                 # plan | fact | chat
    intent_reason: str
    conditions: dict            # watch_date, start_after, end_before, region, genre
    ask: str | None             # 되묻기 문구 (있으면 Tool을 부르지 않고 바로 respond)
    plan: list[dict]            # [{tool, args}]
    cache: dict                 # "tool|args_json" → Tool 결과
    results: dict               # tool 이름 → 결과(들)
    judged: dict                # fit[], unfit[], excluded[], window_min, notes[]
    replan_count: int
    replan_history: list[dict]  # [{count, reason, strategy}]
    answer: str
```

### 4.3 제약 판단 계산식 (F3008)
- `AD_BUFFER = 20분` (광고와 입장 시간, 설정값)
- `need = show_tm + AD_BUFFER`
- 시작 시각과 끝 시각이 모두 있을 때:
  - `latest_start = end_before − need`
  - **맞음** 조건: `start_after ≤ latest_start`
  - 맞는 영화 → "**start_after ~ latest_start 사이에 시작하는 회차**를 고르세요"
- 끝 시각이 없을 때: 모두 맞음으로 보고, `예상 종료 = start_after + need`를 보여 준다.
- **상영 시각표는 API로 확인할 수 없다.** 그래서 시작 시각을 지어내지 않고, 늦어도 시작해야 하는 시각(`latest_start`)만 역산해 제시한다.
- `genre`가 있으면 genres에 그 장르가 없는 영화는 맞지 않음(사유: 장르)으로 둔다.
- NO_RUNTIME이나 NOT_FOUND인 영화는 판단하지 않고 제외하며, 사유를 함께 남긴다.

### 4.4 재계획 (F3009, NF3004)
- **재계획하는 경우**: 판단 결과 맞는 영화가 0편이고, 아래 전략이 아직 남아 있을 때
- **재계획하지 않는 경우**
  - 후보 Tool이 INVALID_KEY나 UPSTREAM_ERROR로 실패했을 때 → 바로 안내한다
  - 되묻기 상황일 때
  - `fact`나 `chat` 의도일 때
- **전략** (순서대로 적용, 이미 받은 결과는 cache로 재사용)

| 회차 | 전략 | 이유 |
|---|---|---|
| 1 | 박스오피스 후보를 상위 5편에서 10편으로 확장 | 후보 수 늘리기 |
| 2 | TMDB 신작 보충 (아직 안 했다면) | 다른 출처에서 후보 찾기 |
| 3 | 선호 조건(`genre`) 완화 | 선호 조건은 지켜도 되고 안 지켜도 되지만 제약 조건은 반드시 지켜야 한다 |

- 적용할 전략이 없는 회차는 건너뛴다.
- **상한 `MAX_REPLAN = 3`**. 상한에 도달하면 멈추고, 가장 짧은 필요 시간과 실제 시간 범위를 근거로 조건을 조정하라고 되묻는다.

### 4.5 대화 맥락 (F3010)
- **보관 단위**: session_id. 서버 메모리의 dict에 둔다.
- **보관하는 것**
  - 마지막 `conditions`
  - 마지막 추천 요약: `[{movie_nm, show_tm, fit, latest_start}]`
  - 최근 대화 3턴 (사용자 메시지와 답변 원문)
- **보관하지 않는 것**: Tool 원본 응답, API 키, 이벤트
- **갱신 방법**: 새로 추출한 조건 중 null이 아닌 값만 이전 조건 위에 덮어쓴다.
  - "같은 조건으로 홍대에서" → `region`만 바뀐다.
- `analyze`의 프롬프트에 이전 조건과 최근 대화를 넣는다. "그거", "같은 날" 같은 말을 해석하기 위해서다.

  - LLM을 쓰지 않는다.
  - 저장 중 예외가 나면 삼킨다. 대화는 계속되어야 한다.

### 5.2 DB (SQLite, `data/app.db`)
```sql
CREATE TABLE plans (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  movie_nm TEXT NOT NULL,
  watch_date TEXT NOT NULL,     -- YYYY-MM-DD
  start_time TEXT NOT NULL,     -- HH:MM
  end_time TEXT NOT NULL,       -- HH:MM
  theater TEXT, memo TEXT,
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);
CREATE TABLE event_logs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id TEXT NOT NULL, run_id TEXT NOT NULL, seq INTEGER NOT NULL,
  event TEXT NOT NULL, ts TEXT NOT NULL, payload TEXT NOT NULL  -- JSON
);
CREATE INDEX idx_logs_session ON event_logs(session_id, id);
```

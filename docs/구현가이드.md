## M0. 기획 검증 — API 4종 호출 확인 (기획서 7절)

### ① 구현 명세
- 파일: `scripts/check_apis.py` (1회용 확인 스크립트. Tool 코드와는 별개다)
- 할 일: GMS, KOBIS(2개 엔드포인트), TMDB(2개 엔드포인트), 카카오를 각각 1회 호출한다. 응답에서 **기획서 3.3절의 출력 필드에 해당하는 값**만 뽑아 출력한다.
- 값이 비어 있는 경우도 일부러 호출해 본다: 없는 movieCd, 결과가 없는 지역명(예: "zzzz"), 틀린 키.
- 결과를 기획서 1.2절 표(호출 한도, 약관)와 7절 체크박스에 기록한다.

### ② 힌트
- **키 발급**
  - TMDB: themoviedb.org에 가입 → 계정 설정 → API → 개발자용 키를 신청한다. "API Key"(v3)를 쓴다.
  - 카카오: developers.kakao.com → 내 애플리케이션 → 앱 추가 → **REST API 키**를 쓴다.
    - 호출했을 때 403이나 권한 오류가 나면, 앱 설정에서 카카오맵(로컬) 사용 설정이 켜져 있는지 확인한다.
- **인증 방식이 API마다 다르다.**
  - KOBIS와 TMDB는 쿼리 파라미터로 보낸다 (`key=`, `api_key=`).
  - 카카오는 **헤더**로 보낸다 (`Authorization: KakaoAK {키}`).
- `requests.get(url, params=..., headers=..., timeout=10)`. 한글 쿼리는 `params`에 넣으면 인코딩이 자동으로 된다.
- KOBIS는 키가 틀려도 **HTTP 200**을 주고, 본문에 `faultInfo`를 넣어 보낸다. TMDB와 카카오는 키가 틀리면 **401**을 준다. 이 차이가 Tool 실패 코드 설계로 이어진다.
- `.env`를 루트에 두고 `load_dotenv()`로 읽는다. 출력에 키가 찍히지 않게 주의한다.

### ③ 예시
확인해야 할 응답 경로:
```
KOBIS 박스오피스  body["boxOfficeResult"]["dailyBoxOfficeList"][i] → rank, movieCd, movieNm, openDt
KOBIS 영화상세    body["movieInfoResult"]["movieInfo"] → movieNm, showTm, genres[].genreNm, audits[].watchGradeNm
KOBIS 키 오류     body["faultInfo"]["message"]
TMDB discover    body["results"][i] → id, title, release_date
TMDB movie/{id}  body["runtime"]   (0이나 null이 올 수 있는지 확인)
카카오 키워드     body["documents"][i] → place_name, road_address_name, place_url, phone ; body["meta"]["total_count"]
```
일반적인 헤더 인증 문법 (예시 URL):
```python
requests.get("https://example.com/search", params={"q": "검색어"},
             headers={"Authorization": "Bearer abc"}, timeout=10)
```

### ② 힌트
- `uvicorn app.main:app`은 `backend/` 폴더에서 실행한다. 그래야 `app`이 패키지로 잡힌다.

- `conn.row_factory = sqlite3.Row`를 설정하면 결과를 `dict(row)`로 바꾸기 쉽다.

## M2. Tool 4종 (F3001 ~ F3004)

### ① 구현 명세
| 파일 | 내용 |
|---|---|
| `tools/base.py` 🤖 | `ok()`, `fail()`, `Tool` 데이터클래스(name, description, parameters, func, **kind**), `scrub()` |
| `tools/kobis.py` 🧑 | `get_box_office(target_date="", top_n=5)`, `get_movie_detail(movie_cd)` |
| `tools/kakao.py` 🧑 | `search_theaters(region, size=5)` |
| `tools/tmdb.py` 🧑 | `search_new_releases(from_date, to_date)` |
| `tools/registry.py` | `TOOLS: dict[name, Tool]`, `catalog()` → `[{name, description, parameters}]`. kind는 넘기지 않는다 |
| `scripts/try_tools.py` | Tool마다 정상 1회, 잘못된 입력 1회, 키 없음 1회, 결과 없음 1회 (체크리스트 1~4) |

입출력과 실패 코드는 기획서 3.3절을 그대로 따른다.

### ② 힌트
- **샘플 버그를 같이 고친다** (`.claude/REFERENCE.md` 4절)
  - `requests.get`에 timeout이 없다.
  - 날짜 형식이 틀리면 `ValueError`가 나는데, 이게 UPSTREAM_ERROR로 잘못 분류된다.
  - 날짜 파싱은 함수 안에서 먼저 try로 감싸 **BAD_ARGUMENT**를 돌려준다.
- **scrub**: 샘플 정규식 `\b(key|apikey|token)=`는 `api_key=`를 잡지 못한다. `_`도 단어 문자라서 `key` 앞에 `\b` 경계가 생기지 않기 때문이다. 키 **값**으로 가리는 목록에 4개 키를 모두 넣는다.
- **HTTP 상태별로 분기하는 순서**
  - 401 / 403 → INVALID_KEY
  - 그 밖의 4xx / 5xx와 `RequestException` → UPSTREAM_ERROR
  - `raise_for_status()`를 바로 부르면 401도 예외 하나로 뭉뚱그려진다. 그래서 `status_code`를 **먼저** 확인한다.
- **원본 응답을 통째로 넘기지 않는다.** 판단에 쓸 값만 뽑는다. 빈 값을 `""`나 `0`으로 채우지 않는다.
  - TMDB의 `runtime: 0`은 "모른다"는 뜻이므로 `None`으로 둔다.
- `get_box_office`의 `itemPerPage`는 KOBIS 최대값이 10이다. `top_n`을 1~10으로 검증한다.
- **TMDB 주의**
  - discover 결과는 여러 쪽(page)으로 나뉘어 온다. 첫 쪽에서 앞의 3편만 쓴다.
  - 상세 조회가 영화마다 1번씩 더 필요하므로 호출 수에 주의한다.
- **Tool 설명(description)에는 "언제 부르는지"를 쓴다.** 예: "~할 때 부른다". 기능 이름만 적으면 LLM이 Tool을 잘 고르지 못한다.

### ③ 예시
실패 코드를 판정하는 흐름 (의사코드):
```
call_api(url, params, headers):
    키가 없으면                    → (None, fail INVALID_KEY)
    요청 (timeout)
      네트워크 예외                → (None, fail UPSTREAM_ERROR)
    status 401/403               → (None, fail INVALID_KEY)
    status >= 400                → (None, fail UPSTREAM_ERROR)
    본문에 API 고유의 오류 표시    → (None, fail ...)
    → (body, None)
```
`try_tools.py`의 기대 출력 형태:
```
[Tool] get_box_office (external) — 볼 영화를 아직 정하지 않았을 때 ...
True  정상        → {'basis_date': '2026-11-18', 'is_estimated': True, 'movies': [...]}
False 잘못된 날짜  → BAD_ARGUMENT
False 키 없음     → INVALID_KEY
False 결과 없음   → NO_DATA
```

### ④ 완료 기준 (체크리스트 1~4)
- [ ] `catalog()` 출력이 기획서 3.3절과 일치한다.
- [ ] 모든 실패 경우에서 예외가 밖으로 나오지 않는다.
- [ ] 날짜 없이 부르면 기본값(오늘 → 어제 기준)이 적용된다. 미래 날짜는 `is_estimated: true`가 된다.

## M3. 제약 판단 `judge.py` + 테스트 (F3008) 🧑

### ① 구현 명세
**순수 함수**로 만든다. LLM, 네트워크, 전역 상태에 의존하지 않는다.
```
to_min("14:30") -> 870
to_hhmm(870) -> "14:30"
evaluate(movies, conditions, ad_buffer) -> {
    fit:      [{movie_nm, show_tm, need_min, latest_start, source}],
    unfit:    [{movie_nm, show_tm, need_min, reason}],
    excluded: [{movie_nm, code, reason}],      # NO_RUNTIME, NOT_FOUND 등
    window_min: int | None,
    notes: [str]                               # "날짜 미지정 → 오늘 기준" 같은 안내
}
```
- 입력 `movies`: execute 단계에서 정리한 후보 목록. 항목마다 `show_tm`이 있거나, 실패 코드가 있다.

### ② 힌트
- 시각은 **분 단위 정수**로 바꿔 계산한다. `datetime`보다 단순하고 테스트하기 쉽다.
- 경우 나누기
  - 끝 시각 없음 → 모두 fit. `expected_end`를 넣는다.
  - 시작과 끝이 모두 있음 → `latest_start = end − need`, `start ≤ latest_start`이면 fit.
  - 장르 조건 → 장르가 맞지 않으면 unfit, 사유는 "장르".
- unfit 사유에는 **숫자**를 넣는다. 예: "필요 159분 > 가능 150분". 이 숫자가 그대로 답변의 근거가 된다 (F3011).
- 자정을 넘기는 경우(23시 → 01시)는 이번 범위 밖이다. analyze 단계의 되묻기 규칙에서 막는다.

### ③ 예시 (테스트 케이스)
| start | end | show_tm | buffer | 기대 |
|---|---|---|---|---|
| 14:00 | 19:00 | 132 | 20 | fit, latest_start 16:28 |
| 15:00 | 17:30 | 141 | 20 | unfit (필요 161 > 가능 150) |
| 15:00 | None | 120 | 20 | fit, expected_end 17:20 |
| 15:00 | 19:00 | None(NO_RUNTIME) | 20 | excluded |

일반적인 pytest 문법:
```python
def test_something():
    assert add(1, 2) == 3
```

## M4. 그래프 + 노드 (F3005 ~ F3007, F3011) 🧑

### ① 구현 명세
- `llm.py`
  - `ChatOpenAI`(GMS) 객체를 만든다.
  - 구조화 출력용 Pydantic 모델 `Analysis`를 정의한다.
    - `intent: Literal["plan","fact","chat"]`, `reason: str`
    - `watch_date`, `start_after`, `end_before`, `region`, `genre`: 모두 `Optional`

  - analyze 다음은 분기한다 (ask 또는 chat → respond, 그 외 → plan).
  - plan → execute → judge 순서로 잇는다.
  - judge 다음은 분기한다 (재계획 → plan, 그 외 → respond).

- **analyze 프롬프트에 넣을 것**
  - 오늘 날짜와 요일 ("내일", "토요일"을 날짜로 바꾸려면 꼭 필요하다)
  - `catalog()`
  - 이전 조건 (M6)
  - 규칙: "말하지 않은 값은 null"
- LLM이 돌려준 `tools`는 **그대로 믿지 않는다.** plan 노드의 코드가 걸러 낸다.
  - 레지스트리에 없는 Tool은 버린다.
  - 의존 순서(박스오피스 → 상세)를 맞춘다.
  - `region`이 없으면 영화관 검색을 뺀다.
  - 미래 날짜일 때만 TMDB를 넣는다.
- **execute 노드**
  - 상세 조회는 박스오피스 결과의 `movie_cd`마다 반복해서 호출한다.
  - TMDB 결과는 이미 러닝타임이 들어 있으므로 상세 조회를 하지 않는다.
  - 공백을 지운 제목으로 같은 영화를 합친다.
- **respond 프롬프트**
  - "아래 판단 결과에 있는 숫자와 시각만 사용하라. 상영 시각을 지어내지 말라."

- 그래프 구조를 출력할 때는 `app.get_graph().draw_mermaid()`를 쓴다 (검증 4.2).
- `analyze`가 LLM 오류로 실패하면? try로 감싸 `intent="chat"`과 안내 문구로 대신 응답한다 (NF3003).

## M5. 재계획 (F3009, NF3004) 🧑

### ① 구현 명세
- `replan.py`: `next_strategy(state) -> (name, patch) | None`
  - 기획서 4.4절의 전략표를 순서대로 확인한다.
  - 적용할 수 있는 전략이 없거나 상한에 도달하면 `None`을 돌려준다.
- judge 다음 분기
  - 맞는 영화가 0편이고, 후보 Tool이 치명적 실패가 아니고, `next_strategy`가 있으면 → plan으로 돌아간다 (`replan_count += 1`).
  - 그 외 → respond.
- execute의 **cache**: 키 = `tool 이름 + 정렬한 인자 JSON`. cache에 있으면 Tool을 호출하지 않는다.
- 상한에 도달했을 때: `judged.notes`에 "가장 짧은 필요 시간 N분, 가능한 시간 M분"을 넣는다. respond는 이 내용으로 조건 조정을 되묻는다.

### ② 힌트
- **cache를 확인하는 방법**: 재계획 1회차(5편 → 10편 확장) 때 `tool.call` 이벤트를 세어 본다. 처음 5편의 상세 조회는 다시 나오면 안 된다.
- 재계획 상한은 코드에도 두지만, LangGraph의 `recursion_limit`도 안전장치가 된다. 기본값은 25다.
- "후보 Tool이 치명적 실패"인지는 박스오피스 결과의 code가 INVALID_KEY나 UPSTREAM_ERROR인지로 판단한다.

### ③ 예시
cache 키 (일반 문법):
```python
json.dumps({"movie_cd": "2024..."}, sort_keys=True, ensure_ascii=False)
```
R2의 이벤트 흐름 예:
```
tool.call get_box_office {top_n:5} → 상세 5회 → judge: fit 0
replan {count:1, strategy:"expand_top_n"}
tool.call get_box_office {top_n:10} → 상세 5회 (새로운 5편만) → judge: fit 2 → respond
```

### ④ 완료 기준 (체크리스트 9, 10)
- [ ] R2: 재계획이 1회 이상 일어나고, 이미 조회한 상세는 다시 호출하지 않는다.
- [ ] R3: 재계획 3회 후 멈추고, 근거 숫자와 함께 조건 조정을 되묻는다.

## M6. 대화 맥락 `memory.py` (F3010) 🧑

### ① 구현 명세
- `get(session_id) -> dict`, `update(session_id, conditions, recommendations, user, answer)`
- `merge_conditions(prev, new) -> dict`: new에서 null이 아닌 값만 prev 위에 덮어쓴다.
- 보관하는 것과 보관하지 않는 것은 기획서 4.5절을 따른다. 최근 3턴만 둔다.

### ② 힌트

- 반대로 "같은 날", "아까 그거" 같은 말을 해석하려면 LLM이 이전 조건을 알아야 한다. 그래서 프롬프트에도 이전 조건을 넣는다.
- 사용자가 값을 **지우고 싶을 때**("지역은 상관없어")는 이번 범위 밖이다. 알려진 한계로 기록한다.

### ④ 완료 기준 (체크리스트 11)
- [ ] R1 다음 R7: `region`만 바뀌고 `watch_date`, `start_after`, `end_before`는 유지된다.

## M7. 이벤트 + 로깅 Agent (F3012, F3013) 🧑

### ① 구현 명세
- `events/bus.py`: 샘플의 EventBus를 바탕으로 만든다. 공통 형식에 `run_id`와 `seq`를 더한다 (기획서 5.1).
- 노드마다 `step.enter`, `step.exit`(elapsed_ms 포함)를 발행한다. 샘플의 `traced` 래퍼를 쓴다.
- execute에서 `tool.call`, `tool.result`(ok, code, elapsed_ms)를 발행한다.
- analyze에서 `decision{kind:"intent", value, reason}`, 되묻기면 `decision{kind:"ask"}`를 발행한다. 재계획 때는 `replan`을 발행한다.
- `events/logger_agent.py`: `handle(msg)` → `event_logs`에 INSERT. 앱이 시작할 때 `bus.subscribe(handle)`.

### ② 힌트
- 메인 Agent 코드에서 `logger_agent`를 **import하지 않는다.** 연결은 `main.py` 한 곳에서만 한다. 이렇게 해야 "구독을 빼도 동작"(체크리스트 15)을 확인할 수 있다.
- `payload`는 `json.dumps(..., ensure_ascii=False)`로 저장한다.
- 저장 실패 시험: handle 안에서 일부러 예외를 던져 본다. 그래도 bus가 삼키기 때문에 대화는 계속된다 (체크리스트 17).
- `/api/chat` 응답에 넣을 `events[]`: 요청마다 **run_id로 거르는 임시 구독자**를 붙였다가 떼면 된다.
  - 다른 방법: 요청이 끝난 뒤 DB에서 해당 run_id의 이벤트를 조회한다. 이 방법은 로깅 Agent에 의존하게 되는데, 장단점을 생각해 본다.
- 소요 시간은 `time.perf_counter()`의 차이를 1000배해 ms로 만든다.

### ④ 완료 기준 (체크리스트 14 ~ 17)
- [ ] 세션 2개를 실행해도 로그가 섞이지 않는다.
- [ ] `decision` 이벤트에 의도와 이유가 남는다.
- [ ] 구독을 빼도 응답이 정상으로 나온다. 저장을 실패시켜도 응답이 정상으로 나온다.

## M8. FastAPI (F3014 ~ F3017)

### ① 구현 명세
- 기획서 5.3절의 표대로 라우터 4개를 만든다: `chat`, `plans`, `logs`, `health`. 요청과 응답은 `schemas.py`의 Pydantic 모델로 정의한다.

- **chat** 🧑
  - session_id가 없으면 새로 발급한다.
  - `session.start`를 발행하고, 그래프를 실행하고, 메모리를 갱신하고, `session.end`를 발행한다.

- logs: 목록은 `GROUP BY session_id`, 상세는 `ORDER BY id`, 삭제는 `DELETE`. **PUT은 없다.**

- chat에서 예외가 나도 500 상세를 그대로 내보내지 않는다. 사용자용 문구와 `notice`만 보낸다 (NF3002).

# 대표 시나리오 검증 기록

- 일시: 2026-11-20 오후
- 방법: `scripts/run_scenarios.py`
  - 실제 GMS LLM과 KOBIS·TMDB·카카오 API를 호출한다.
  - 요청마다 기대 동작을 코드로 점검한다.
- 자동 기록:
  - [`결과.md`](결과.md): 요청별 최종 응답, 단계, Tool 호출, 재계획, 처리 시간
  - [`logs/`](logs): 요청별 전체 이벤트
- 최종 실행 결과: **10개 시나리오, 점검 79개 모두 통과**

## 1. 대표 요청과 다섯 가지 필수 경우 (명세 4장)

| 번호 | 경우 | 요청 | 결과 | 처리 시간 |
|---|---|---|---|---|
| R1 | **한 번에 충족** | 내일 강남에서 2시 이후에 영화 보고 7시 전에 끝내고 싶어 | 5편 모두 맞음. 늦어도 시작할 시각(예: 폭설 17:12)을 제시하고 영화관 5곳을 안내 | 약 8~9초 |
| R2 | **재계획** | 내일 3시 이후에 보고 4시 45분 전에 끝나야 해 | 상위 5편으로 0편 → 10편으로 확장. 앞 5편의 상세는 cache로 재사용 → 1편을 찾음 | 약 10~15초 |
| R3 | 재계획 후 전략 소진 | 오늘 3시 이후에 보고 4시 전에 끝나야 해 | 확장 → TMDB(결과 없음) → 남은 전략이 없어 멈춤. "필요 101분 > 가능 60분"을 근거로 조건 조정을 요청 | 약 11~15초 |
| R3b | **상한 도달** | 오늘 3시 이후에 액션 영화 보고 4시 전에 끝나야 해 | 확장 → TMDB → 장르 완화의 **3회 = 상한**에서 멈춤. plan 단계는 4번만 진입(무한 반복 없음) | 약 10~17초 |
| R4 | **Tool 하나 실패** | R1과 같음 (카카오 키를 비움) | 영화관만 INVALID_KEY. 영화 추천은 정상이고 "영화관 정보를 가져오지 못했다"고 안내. 재계획하지 않음 | 약 6~9초 |
| R4b | 후보 Tool 치명적 실패 | R1과 같음 (KOBIS 키를 비움) | 박스오피스가 INVALID_KEY라 재계획하지 않음. 영화관 검색은 계속 진행. "판단하지 못했다. 잠시 후 다시 시도" | 약 4초 |
| R5 | **Tool 불필요** | 안녕! 뭘 할 수 있어? | chat. Tool 호출 0건이고 plan·execute·judge를 건너뜀 | 약 3초 |
| R6 | 되묻기 | 7시 전에 끝나는 영화 알려줘 | Tool 호출 0건. "19:00 전에 끝나야 한다고 하셨는데, 몇 시부터 볼 수 있으세요?" | 약 1.5초 |
| R7 | 대화 맥락 | (R1 다음 턴) 같은 조건으로 홍대에서 | 바뀐 조건은 region뿐. 새 호출은 영화관 1건이고 나머지 6건은 cache 재사용 | 약 5초 |
| R8 | 미래 날짜 | 이번 주 토요일 2시 이후, 7시 전 | 관람일 2026-11-21. "11월 19일 집계 기준이라 추정"이라고 밝힘 | 약 6~8초 |

**처리 시간 (NF3005)**
- 대부분 15초 이내다.
- 시간의 대부분은 LLM 2회(analyze, respond)와 KOBIS 상세 조회가 차지한다.
- 화면에는 처리 중 스피너와 경과 초를 보여 준다.
- 외부 API가 응답하지 않으면 HTTP_TIMEOUT(10초)에서 끊고 실패로 처리한다. 그래서 무한정 기다리지 않는다.

## 2. 기대와 다르게 동작한 것: 원인과 수정 내용

자동 점검과 답변 직접 읽기로 찾았다. 아래 일곱 가지를 모두 고친 뒤 다시 실행해 통과를 확인했다.

| # | 발견한 곳 | 기대와 다른 점 | 원인 | 수정 |
|---|---|---|---|---|
| 1 | R3 | "상한 도달"을 보이려 했으나 재계획 2회 뒤 **전략 소진**으로 멈춤 | 장르 조건이 없으면 전략 3(장르 완화)을 적용할 수 없다. 설계대로의 동작이다 | 장르 조건이 있는 **R3b**를 추가해 상한 3회 도달을 따로 검증했다. R3는 "전략 소진" 사례로 남겼다 |
| 2 | R4·R8 | 답변에 `latest_start` 같은 **영어 키 이름이 노출**됨 | LLM에 넘기는 판단 결과 JSON의 키가 영어였다. 프롬프트의 "쓰지 마라"만으로는 막히지 않았다 | 근거 JSON을 한국어 키로 바꿨다(`nodes.respond`). 남는 경우에 대비해 코드가 마지막에 바꾸는 `_no_keys()`를 추가했다 |
| 3 | R4·R8 | 맞는 영화가 있는데도 "시작을 앞당기거나 끝 시각을 늦출 수 있나요?"라고 질문 | 조정 질문을 할지를 LLM 판단에 맡겼다 | 코드가 경우를 나눠 지시한다(0편이면 질문, 1편 이상이면 질문 금지, 후보 Tool 실패면 다시 시도 안내) |
| 4 | R3b·R8 | 집계 기준일을 "집계 기준일 기준"이라고만 하고 **실제 날짜를 말하지 않음**. 안내 문구 "신작 정보 정보를 조회 결과가 없어…"가 어색함 | 날짜 문장을 LLM이 만들게 했다. 안내 문구 조립에 중복이 있었다 | "박스오피스 순위는 11월 19일 집계 기준이라…"와 재계획 경로 문장을 코드가 만들어 넣게 했다. 안내 문구를 "○○ 정보를 가져오지 못했습니다(사유)."로 바꿨다 |
| 5 | R8 | 같은 문장인데 실행에 따라 "7시 전"을 **07:00**으로 읽음. "이번 주 토요일"을 날짜로 바꾸지 못함 → 되묻기로 빠짐 | LLM 출력이 실행마다 다르다 | `_fix_afternoon()`: 끝 시각이 시작보다 이른 오전이면 오후로 본다. 고친 사실은 `llm.decision.code_fixes`에 남긴다. 프롬프트에 앞으로 7일의 날짜표(`_week_table`)를 코드가 계산해 넣었다 |
| 6 | R1 → R7 | R7 점검 실패. 원인을 따라가 보니 R1에서 LLM이 "2시 이후"를 **15:00**으로 뽑았다 | 프롬프트의 예시가 `'3시' → 15:00` 하나여서 숫자에 끌려갔다 | 예시를 여러 개로 바꿨다(2시 이후 → 14:00, 4시 45분 전 → 16:45, 7시 전 → 19:00). R1에 조건 값 점검을 추가했다 |
| 7 | R8 2회차 | KOBIS 시간 초과(UPSTREAM_ERROR) 때 답변이 "가장 짧은 필요 시간: null"이라며 조건 조정을 요청 | 빈 값을 그대로 넘겼다. 후보 Tool 실패를 "0편"과 구분하지 않았다 | 빈 값은 근거에서 뺀다. 후보 Tool이 실패하면 "판단하지 못했다, 잠시 후 다시 시도"로 안내한다. 같은 상황을 고정해서 재현하도록 **R4b**를 추가했다 |
| 8 | R3b | 답변에 프롬프트의 "반드시 넣을 문장:" 제목이 그대로 나옴 | 프롬프트의 구조를 LLM이 따라 썼다 | 제목 없이 본문에 넣으라고 지시를 바꿨다. 지시 문구가 들어간 줄은 코드가 지운다 |

**배운 점**
- **프롬프트는 부탁이고, 코드는 보장이다.**
- 위 문제는 모두 "LLM에게 규칙을 지켜 달라고 했지만 가끔 지키지 않은" 경우다.
- 규칙으로 정할 수 있는 것은 코드로 옮겼다: 말해야 할 문장, 질문을 할지 여부, 키 이름 제거, 오후 해석.
- 같은 요청을 두 번 실행해 결과가 같은지도 확인했다(1차·2차 실행 기록 참고).

## 3. 남은 한계

- **데이터 의존**: R2·R3의 시각은 11/20 박스오피스(러닝타임) 기준으로 정했다. 다른 날에는 재계획이 일어나지 않거나 결과가 달라질 수 있다.
- **TMDB 보충**: R8에서 LLM이 TMDB Tool을 고르지 않는 경우가 많다. 신작 보충은 주로 재계획 전략 2에서 일어난다.
- **기억의 한계**:
  - "지역은 상관없어"처럼 값을 지우는 요청은 표현할 수 없다. merge가 null을 "말하지 않음"으로 읽는다.
  - 서버를 재시작하면 대화 기억과 cache가 사라진다(메모리 dict).
- **상영 시각표**: API로 확인할 수 없다. 그래서 "늦어도 몇 시에 시작"이라는 기준만 제시한다(F3008 설계대로).

# 요구사항 정의서 · MoviePlanner Agent

- 작성: 최진욱
- 작성일: 2026-11-20
- 대상: SSAFY AI 코어 프로젝트 3회차 (명세 6장 "1) 요구사항 정의서")
- 범위: **필수 기능 F3001~F3019, 비기능 NF3001~NF3007.** 심화 기능 F3020~F3023은 선택하지 않았다.

## 1. 서비스 개요

사용자가 말한 **시간 조건**을 이해하고, 실제 박스오피스·러닝타임·영화관 정보를 외부 API로 확인한 뒤 **그 시간 안에 볼 수 있는 영화**와 **늦어도 몇 시에 시작해야 하는지**를 알려 주는 Agent다.
- 조건에 맞는 영화가 없으면 스스로 계획을 바꿔 다시 찾는다(최대 3회).
- 추천받은 영화는 관람 계획으로 저장·수정·삭제할 수 있다.

**대표 요청**: "내일 강남에서 2시 이후에 영화 보고 7시 전에 끝내고 싶어"

## 2. 도메인 선택과 조건 충족 근거 (명세 2.1)

### 2.1 외부 API 3종: 서로 다른 정보

| API | 주는 정보 | 쓰는 곳 |
|---|---|---|
| **KOBIS 오픈API** (영화진흥위원회) | 일별 박스오피스(후보 영화), 영화 상세(러닝타임·관람등급·장르) | 후보 목록, 시간 판단의 근거 |
| **TMDB API** | 박스오피스 집계에 아직 없는 신작과 그 러닝타임 | 미래 날짜의 후보 보충 (재계획 전략 2) |
| **카카오 로컬 API** | 지역 영화관의 이름·주소·링크 | 보조 정보 |

출처와 이용 조건(호출 한도, 약관, 출처 표기)은 README "외부 API 출처와 이용 조건"과 `docs/기획서.md` 1.2절에 기록했다(NF3007).

### 2.2 Tool 결과와 사용자 제약을 비교해야만 답할 수 있는 요청

| 요청 | Tool 없이 LLM만으로 답하면 틀리는 점 |
|---|---|
| "내일 강남에서 2시 이후에 보고 7시 전에 끝내고 싶어" | 지금 상영작과 러닝타임을 모른다. 내려간 영화를 추천하거나 러닝타임을 지어내 7시를 넘긴다 |
| "이번 주 토요일 2시 이후, 7시 전" | 학습 시점 이후의 개봉작을 모르고, 시간 계산의 근거가 없다 |
| "오늘 3시 이후에 보고 4시 전에 끝나야 해" | 맞는 영화가 없는데도 있다고 지어낸다. "가장 짧은 영화도 101분이 필요한데 가능한 시간은 60분"이라는 근거를 대지 못한다 |

M0에서 확인한 사례가 있다. GMS LLM에 "어제 박스오피스 1위"를 묻자 조회할 수 없다며 거절했다. 실제 1위 '폭설(88분)'은 KOBIS로만 확인됐다.

### 2.3 재계획이 의미 있는 이유
- 처음 후보(박스오피스 상위 5편) 안에 맞는 영화가 없어도, 후보를 넓히거나(10편) 다른 출처(TMDB)를 더하거나 선호 조건(장르)을 풀면 맞는 영화가 생길 수 있다.
- 실제 R2에서는 5편 중 0편이었다. 10편으로 넓히자 1편(81분 영화)을 찾았다.

### 2.4 저장할 결과물
**관람 계획**: 영화명, 관람 날짜, 시작 시각, 종료 시각, 영화관(선택), 메모(선택), 생성 일시, 수정 일시. 저장·조회·수정·삭제를 할 수 있다.

### 2.5 위험 도메인 여부
해당하지 않는다(건강·금융 아님). 전문가 조언 면책 문구는 두지 않는다(체크리스트 13: 해당없음).

## 3. 조건과 의도 (명세 2.2)

### 3.1 조건 3종

| 구분 | 필드 | 예 | 비어 있을 때 |
|---|---|---|---|
| 기준 | `watch_date` | "내일" → 2026-11-21 | 오늘로 조회한다 |
| 기준 | `start_after` | "2시 이후" → 14:00 | `end_before`만 있으면 Tool을 부르기 전에 **되묻는다** |
| 선호 | `region` | 강남 | 영화관 검색을 하지 않는다 |
| 선호 | `genre` | 액션 | 장르로 거르지 않는다. 재계획 3단계에서 풀 수 있다 |
| 제약 | `end_before` | "7시 전" → 19:00 | 시간 제약 없이 예상 종료 시각만 보여 준다 |

- LLM은 이번 메시지에 나온 값만 채우고, 나머지는 null로 둔다.
- 영화 관람 맥락에서 1~11시는 오후로 해석한다.
- 끝 시각이 시작보다 이른 오전으로 나오면 코드가 오후로 고친다(`_fix_afternoon`).

### 3.2 의도

| 의도 | 처리 |
|---|---|
| `plan` | 계획 → 실행 → 판단 → (재계획) → 응답 |
| `fact` | plan과 같은 경로(후보와 상세 조회 후 응답). 시간 조건이 없으면 모두 '맞음'으로 두고 러닝타임과 예상 종료 시각을 보여 준다 |
| `chat` | Tool 없이 바로 응답 |

명세의 의도 5종 중 "계획 확정"은 화면의 [계획 저장] 버튼과 `POST /api/plans`로 처리한다. 사용자가 이미 고른 값을 저장하는 일이라 LLM의 판단이 필요 없기 때문이다. "캘린더 등록"은 심화라 범위에서 뺐다.

### 3.3 되묻기 (코드가 판정, Tool 호출 전)
- `end_before`는 있는데 `start_after`가 없을 때 → "19:00 전에 끝나야 한다고 하셨는데, 몇 시부터 볼 수 있으세요?"
- `start_after ≥ end_before`일 때 → "시작 가능 시각이 끝나야 하는 시각보다 늦어요. 시각을 다시 알려 주세요."

## 6. 기획 검증 결과 (명세 2.7)

### 6.1 외부 API 호출 확인 (2026-11-19, `scripts/check_apis.py`)

| API | 결과 | 확인한 사실 |
|---|---|---|
| KOBIS 박스오피스 | 어제 날짜 HTTP 200·10건 / 오늘 날짜 HTTP 200·**빈 리스트** | 오늘·미래는 집계가 없다 → 기준일을 "어제"로 바꾸고 추정임을 밝히는 설계(F3002) |
| KOBIS 상세 | `showTm`이 **문자열**("88") | 정수로 바꿔서 판단 |
| TMDB discover/상세 | HTTP 200·22건, `runtime`은 정수 | 미래 개봉작은 `runtime=0` → null로 처리 |
| 카카오 로컬 | "강남 영화관" CT1 HTTP 200·22건 | 이름·주소·링크 추출 |
| GMS LLM | 인사 정상, "어제 1위"는 거절 | Tool 없이는 답할 수 없음을 확인 |

### 6.2 실패·빈 응답 확인 (`check_apis.py fail`)

| 상황 | 실제 응답 | 설계 반영 |
|---|---|---|
| KOBIS 틀린 키 | HTTP 200 + `faultInfo.errorCode=320010` | HTTP 상태가 아니라 본문으로 판별: 320010 → INVALID_KEY, 그 밖 → BAD_ARGUMENT |
| KOBIS 없는 movieCd | HTTP 200, 모든 값 None | movieCd가 None → NOT_FOUND |
| 카카오 틀린 키 | HTTP 401, **메시지에 키 원문 포함** | `scrub()`에 `appKey(...)` 패턴 추가(NF3002) |
| TMDB 미래작 | `runtime: 0` | 0을 null로 → NO_RUNTIME으로 제외 |

### 6.3 Tool 출력 구조 대조, 설계 시험, 설계 변경

**출력 구조 대조**
- 실제 응답의 키를 Tool 출력 구조와 대조했다.
  - KOBIS: `movieCd`, `movieNm`, `showTm`, `audits`, `genres`
  - TMDB: `runtime`
  - 카카오: `place_name`, `road_address_name`, `place_url`
- Tool은 판단에 쓸 값만 골라 담는다.

**LLM Tool 선택 시험**
- catalog를 넘겼을 때 R5(인사)는 `tools=[]`였다.
- R1은 실행마다 고르는 Tool이 달랐다.
- plan 노드가 후보 → 상세를 의존 순서로 **항상** 넣으므로 결과는 같다. LLM이 Tool을 빠뜨려도 계획이 깨지지 않는 설계다.

**대표 요청 따라가기**: R1의 실행 로그에서 `movie_cd`가 상세 조회의 입력으로 전달되는 것을 확인했다.

**검증 중 바뀐 설계**
- R2·R3의 시각을 실제 데이터에 맞게 조정했다. 상한 3회 사례는 장르 조건을 넣은 R3b로 따로 검증했다.
